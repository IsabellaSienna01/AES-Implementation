# Protocol Specification — KDC Key Distribution and Secure Messaging

**Status:** Draft v1.0 for coursework  
**Entities:** Alice (A), Bob (B), KDC  
**Transport:** TCP  
**Cryptographic primitive:** manually implemented AES-128  
**Important:** this document formalizes the assignment's five-step flow. It is a teaching/demo protocol, not a production-ready security protocol.

## 1. Network deployment

Run KDC, Alice, and Bob as separate processes on three distinct, mutually reachable IP addresses. Configure host and port through command-line arguments or a config file; do not hard-code deployment addresses.

Example configuration only (replace with addresses from the actual lab network):

| Entity | Example address | Example port |
|---|---|---:|
| KDC | `10.0.0.10` | `5000` |
| Alice | `10.0.0.11` | `5001` |
| Bob | `10.0.0.12` | `5002` |

Alice opens a TCP connection to KDC. Bob listens for Alice's ticket and subsequent session traffic. For two-way chat, the same established Alice–Bob TCP connection may carry messages in both directions; each endpoint must implement both send and receive logic. KDC is not a relay for chat messages.

## 2. Notation and key material

- `A`, `B`: configured identity strings for Alice and Bob.
- `Ka`: 16-byte long-term ASCII key shared only by Alice and KDC.
- `Kb`: 16-byte long-term ASCII key shared only by Bob and KDC.
- `Ks`: fresh 16-byte session key generated by KDC for Alice–Bob.
- `N1`, `N2`: fresh 16-byte nonces generated using a cryptographically secure random source.
- `E(K, P)`: encrypt serialized plaintext `P` under AES-128-CBC with PKCS#7 padding and a fresh 16-byte IV. The wire representation of an encrypted object is `IV || ciphertext`; both are binary fields. IV is not secret.
- `f(N2)`: the agreed response function. For this draft, interpret `N2` as a 16-byte big-endian unsigned byte string and compute `N2 + 1` modulo 2^128. This operation is performed bytewise with carry. Alice and Bob must implement exactly the same rule.
- `||`: concatenation of fields according to the explicit serialization format below, not ambiguous raw string concatenation.

**Key configuration:** Ka and Kb must be provided at runtime/configuration time and must each contain exactly 16 ASCII bytes. In a teaching setup, configure the same Ka in Alice and KDC, and the same Kb in Bob and KDC. Do not print or commit real keys. KDC generates Ks randomly for each session.

## 3. TCP framing

Every TCP message is framed as:

`uint32_be(payload_length) || payload`

`payload_length` is the number of bytes after the 4-byte header. Maximum is 1 MiB. The receiver must read the entire header and then the entire payload, or report disconnect/timeout. Do not assume one `send()` maps to one `recv()`.

Each payload starts with:
- `version`: 1 byte; value `0x01`.
- `message_type`: 1 byte.
- Remaining fields are defined below.

Use fixed-size fields where specified and 2-byte unsigned big-endian length prefixes for variable-size IDs and encrypted objects. Reject malformed, oversized, truncated, or trailing data.

Message type values:

| Value | Name | Direction |
|---:|---|---|
| `0x01` | `KDC_REQUEST` | Alice → KDC |
| `0x02` | `KDC_RESPONSE` | KDC → Alice |
| `0x03` | `BOB_TICKET` | Alice → Bob |
| `0x04` | `CHALLENGE` | Bob → Alice |
| `0x05` | `CHALLENGE_RESPONSE` | Alice → Bob |
| `0x06` | `CHAT_MESSAGE` | Alice ↔ Bob |
| `0x7F` | `ERROR` | Any → peer |

For a 2-byte length-prefixed field: `uint16_be(length) || bytes`. All integer lengths are unsigned and big-endian.

## 4. Five required protocol steps

### Step 1 — Alice requests a session key

Alice generates `N1` and sends `KDC_REQUEST` to KDC.

Payload fields after the common 2-byte header:
1. `ID_A`: length-prefixed ASCII ID, 1–32 bytes.
2. `ID_B`: length-prefixed ASCII ID, 1–32 bytes.
3. `N1`: exactly 16 bytes.

KDC validates the IDs, checks that the request is structurally valid and that the requested identities are configured/allowed. KDC generates a new random `Ks` for this request.

### Step 2 — KDC returns Alice's encrypted part and Bob's ticket

KDC constructs two independently encrypted objects:

`P_A = Ks(16 bytes) || ID_A(length-prefixed) || ID_B(length-prefixed) || N1(16 bytes)`

`P_B = Ks(16 bytes) || ID_A(length-prefixed)`

Then:
- `C_A = E(Ka, P_A)`
- `T_B = E(Kb, P_B)`

KDC sends `KDC_RESPONSE` with:
1. `C_A`: length-prefixed encrypted object, represented as `IV(16) || ciphertext`.
2. `T_B`: length-prefixed encrypted object, represented as `IV(16) || ciphertext`.

Alice decrypts `C_A` with Ka and verifies `ID_A`, `ID_B`, and `N1` exactly match the request. If any check fails, Alice aborts. Alice obtains Ks and stores `T_B` without decrypting it.

### Step 3 — Alice forwards Bob's ticket

Alice sends `BOB_TICKET` to Bob with:
1. `T_B`: length-prefixed encrypted object.

Bob decrypts `T_B` using Kb, validates the serialized fields, extracts Ks and ID_A, and rejects malformed tickets. The ticket is intended for Bob; Alice must not be able to read or modify its contents successfully.

### Step 4 — Bob challenges Alice

Bob generates fresh `N2` and constructs `P_2 = N2(16 bytes)`. Bob sends `CHALLENGE` to Alice:
1. `C_2 = E(Ks, P_2)`, as a length-prefixed encrypted object (`IV || ciphertext`).

Alice decrypts C_2 using Ks, computes `f(N2)`, and sends the response in Step 5. Bob retains the original N2 and the session state while awaiting the response.

### Step 5 — Alice proves possession of Ks

Alice computes `P_3 = f(N2)` and sends `CHALLENGE_RESPONSE`:
1. `C_3 = E(Ks, P_3)`, as a length-prefixed encrypted object (`IV || ciphertext`).

Bob decrypts C_3 using Ks and compares the recovered 16 bytes to `f(N2)` computed from the challenge it originally sent. If equal, Bob marks the session authenticated. If not equal, Bob rejects and closes/resets the session.

**Important limitation:** this five-step exchange authenticates Alice to Bob, but it does not by itself prove Bob's identity to Alice. If mutual authentication is required, ask the instructor before adding another protocol step, because it changes the required sequence.

## 5. Chat message format

Only authenticated endpoints may send or accept `CHAT_MESSAGE`.

Fields after the common header:
1. `sender_id`: length-prefixed ASCII ID.
2. `sequence_number`: uint64 big-endian.
3. `encrypted_object`: length-prefixed object containing `IV(16) || ciphertext`.
4. `authentication_tag`: length-prefixed tag. If HMAC-SHA-256 is implemented, this is 32 bytes.

Plaintext is ASCII in v1. The ciphertext is held as binary bytes internally and may be printed as lowercase hexadecimal for the demo.

For the recommended integrity profile, compute HMAC-SHA-256 over a canonical byte encoding of:
`version || message_type || sender_id_field || sequence_number || IV || ciphertext`
using a key derived/separated from Ks. Verify the tag in constant time before decrypting. Do not reuse Ks directly for multiple purposes without a documented key-separation approach. If manual HMAC/key derivation is beyond the assignment scope, document that the demo does not provide authenticated message integrity; do not claim tamper resistance.

Sequence numbers start at zero or one (choose one convention and use it on both sides), increase monotonically per sender/session, and duplicates or stale numbers are rejected. Sequence numbers help detect replay only when the receiver tracks state.

## 6. Error messages

`ERROR` payload:
1. `error_code`: uint16 big-endian.
2. `message`: length-prefixed short, non-sensitive description.

Suggested codes:
- `0x0001`: malformed message
- `0x0002`: unsupported version/type
- `0x0003`: invalid identity or state
- `0x0004`: cryptographic validation failed
- `0x0005`: authentication failed
- `0x0006`: message too large
- `0x0007`: timeout or connection failure

Never include secret keys, decrypted tickets, nonce contents, or sensitive plaintext in error messages/logs.

## 7. Required state transitions

Alice:
`Disconnected → ConnectedToKDC → AwaitingKDCResponse → TicketReady → AwaitingChallenge → Authenticated → Chatting`

Bob:
`Listening → TicketReceived → TicketValidated → ChallengeSent → Authenticated → Chatting`

KDC:
`Listening → RequestValidated → SessionKeyCreated → ResponseSent`

Unexpected message types for the current state are rejected. On a failed cryptographic check, authentication failure, malformed frame, or timeout, do not advance to the next state.

## 8. Required test scenarios

1. AES-128 known-answer test vectors pass.
2. Correct Ka/Kb allow the five-step exchange to complete.
3. Alice and Bob hold the same Ks after the exchange.
4. Incorrect Ka prevents Alice from validating the KDC response.
5. Incorrect Kb prevents Bob from opening the ticket.
6. Modified challenge response is rejected.
7. Both directions of chat work over IP-connected processes.
8. Truncated frames, oversized frames, invalid message types, and disconnects are handled.
9. If HMAC is implemented, modified ciphertext/tag is rejected before decryption.
10. Logs do not reveal keys or plaintext.

## 9. Security caveats

This is a coursework protocol draft. The classic symmetric Needham–Schroeder protocol has known replay/session-key freshness limitations in some settings, and this five-step variant does not authenticate Bob back to Alice. CBC provides confidentiality only, not integrity. Production systems should use a vetted protocol and authenticated encryption such as an established AEAD construction from a reputable cryptographic library. Do not deploy this manual implementation for real secrets.
